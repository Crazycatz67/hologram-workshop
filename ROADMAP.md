# Hologram Project — Roadmap

## Revision History

- **2026-09-05 (11):** **Redesigned the core gesture set from live voice-narrated testing** — the most direct feedback the project has gotten so far, and it found two genuine bugs plus one interaction-model rethink:
  - **Bug: pinch failed facing the camera dead-on, worked from the side.** Cause: the "is this really a pinch or a curled fist" guard (`MIN_PINCH_REACH`) measured how far the pinch point sat from the wrist in the 2D camera projection — but a real pinch performed face-on foreshortens in exactly the same way a curled fist does, so the metric could not actually distinguish them across viewing angles; it only ever worked on the one angle it happened to be tuned against. Confirmed on the reported case (reach measured 0.53, well under the 1.05 cutoff, so it *would* have rejected a real pinch) and fixed by removing the reach check entirely.
  - **Bug: `Closed_Fist` didn't register in a "punch" (knuckles-toward-camera) orientation.** That's MediaPipe's own classifier, presumably trained mostly on palm-facing poses — not something fixable in this code directly. Added `isFistShape()` in `gestures.js` as a geometric backstop: true when 3+ non-thumb fingertips sit close to the wrist, which doesn't care which way the hand is turned. `Closed_Fist || isFistShape()` now gates both the pinch-veto and the grab trigger.
  - **Redesign: two-hand pinch-and-twist rotate replaced with single-hand grab-and-twist-your-wrist.** Reported as "janky and cluttered" — holding two simultaneous pinches steady while also twisting them is a genuinely awkward physical motion. A single closed fist now both moves the object (wrist position, as before) *and* spins it (twisting the wrist like turning a doorknob), simultaneously and independently — `gestures.js` gained `handTwist()`, tracking the 2D angle across the index/pinky knuckles rather than fingertips specifically because knuckles stay visible through a closed fist. Twist maps to rotation around the object's *vertical* axis (a lazy-Susan spin) rather than literally the camera-facing roll axis the physical motion actually is — a deliberate stylization, since spinning to see an object's sides is more useful than tipping it in the picture-plane. Two-hand pinch simplifies to scale only.
  - **Fix: the object could be permanently lost off-screen with only manual Reset as recovery** — reported as frustrating during testing. `manipulator.js` now clamps the object's position to stay within a fraction of the visible frustum at its own depth, so a fast or erratic drag can no longer carry it fully out of view.
  - **Explicit priority call, adopted directly:** pause new gestures (explode, push/pull) until the core set (grab/move/rotate/scale) feels reliable. Verified all of the above with synthetic gesture sequences before shipping, same rigor as every other gesture change this session — including reproducing the exact reported pinch failure and confirming the fix, not just trusting the reasoning.

- **2026-09-05 (8):** Built and tested `repair_scan.py` (PyMeshLab, scriptable, no GUI) for the chair's actual topology problem: 2,134 disconnected mesh fragments, 29,654 boundary edges. **Real finding, not a clean win:** `--close-holes` barely helped (2134 -> 2106 components) because most of these fragments are genuinely separate islands, not small gaps in one surface — hole-closing can't weld disconnected pieces together. `--poisson` (Screened Poisson Surface Reconstruction) fixed topology completely (2134 -> 7 components, fully 2-manifold) but **rendered worse with the actual hologram shader**, not better: it smooths past the crop boundary rather than respecting it, so the floor patch under the chair came out bigger and more solid than the simple radius crop alone produces, and one leg tip visibly ballooned where it had been cut from the floor. Confirmed by rendering both versions with `HolographicMaterial` side by side, not by trusting the topology numbers alone. **Decision: not adopting Poisson reconstruction for this scan** — the existing simple crop already looks better in the actual rendered output despite far worse topology stats on paper, a real instance of the efficiency gut-check (a metric improving doesn't mean the visual result improves). The tool is kept for a future scan that has genuinely visible holes on the object itself, which this one — despite the alarming fragmentation count — turned out not to.
- **2026-09-05 (7):** Turned the by-hand crop analysis from Phase 2 into a reusable tool, `analyze_scan.py <path-to-glb>` — no new dependency, uses only `numpy` which was already needed for the original analysis. Given a raw scan, it excludes a bottom slice of the Y range as "probably the floor," estimates an object center from what's left, histograms every vertex's distance from that center, and looks for a genuine empty gap the way the chair's wall was found manually. **Validated against the chair scan itself**, blind to the fact that 0.65 was the known-good answer: it independently found center (-0.029, -0.140) — matching the hand-derived (-0.02, -0.14) almost exactly — and radius 0.594, safely inside the same real gap (0.58-0.77) found by hand, just via a finer sweep. Also stress-tested the failure paths deliberately: an absurd `--floor-fraction` correctly triggers a warning and a clean exit rather than a garbage result, and a less extreme bad value degrades visibly (a skewed center) rather than silently. **What it doesn't do, deliberately:** it only recommends `{center, radius}` — it doesn't apply the crop itself or modify the GLB, so `trimByCylinder()` in `trimGeometry.js` stays the single implementation of the actual cropping logic rather than having two copies (one JS, one Python) to keep in sync. It also can't fix actual holes in the mesh — that's a different problem (see the discussion in chat around this date) with existing free tools (MeshLab's Close Holes / Screened Poisson Reconstruction, or Blender's Remesh) recommended over building custom repair code, which would be disproportionate effort for a solved problem.

- **2026-09-05 (5):** **Fixed a real freeze from live testing.** Reported: gesture control was working, then froze entirely — hand skeleton stuck showing a fist mid-air, model unresponsive, camera orbit also dead. Root cause: `transform`'s hysteresis correctly holds the TRANSFORM mode true for a few frames after a hand drops out (so a momentary two-hand-to-one-hand flicker doesn't cancel the gesture) — but the actual scenario was a genuine two-hand-pinch-to-one-hand-fist transition, and `applyTransform` unconditionally indexed `hands[1]` to compute span/angle. With only one hand actually tracked, that read `undefined.landmarks` and threw. Confirmed by reproducing the exact throw directly (`handSpan(oneHand, undefined, aspect)` → `TypeError: Cannot read properties of undefined (reading 'landmarks')`), then reproducing the full transition through `manipulator.update()` with no crash after the fix. The deeper problem: `renderer.setAnimationLoop` stops scheduling further frames the instant its callback throws uncaught — so one bad frame doesn't just skip a gesture update, it kills rendering, orbit controls, and all future gesture processing permanently, with no visible error and no way to recover short of a reload. Fixed two ways: `manipulator.js` now checks `hands.length` before applying either gesture rather than trusting the stabilized mode alone, and `scene.js`'s render loop now catches and logs any `onTick` exception instead of letting it kill the loop — verified independently by throwing a synthetic error on tick 3 and confirming 114+ further ticks still ran. That second fix is a backstop for whatever the *next* one of these turns out to be, not just this specific bug.

## Phase 1 — Hand Tracking Foundation 🟡 Built 2026-09-05, awaiting a live webcam check

**What got built:** A standalone page (`hands.html` + `hands.js`) — deliberately separate from the 3D viewer, since Phase 4 is where the two merge. Modules mirror the ASL project's pipeline shape:
- `camera.js` — `getUserMedia` setup, teardown, and human-readable messages for the denied/missing/in-use cases.
- `handTracker.js` — MediaPipe `GestureRecognizer` (pinned `@mediapipe/tasks-vision@1.0.1`, `numHands: 2`, GPU delegate, VIDEO mode). `toHands()` flattens MediaPipe's parallel arrays into one object per hand — the normalization seam Phase 4 consumes. Also guards the timestamp: `recognizeForVideo()` throws on any non-increasing timestamp, which would otherwise kill the loop on a repeated frame.
- `gestures.js` — pinch and `isFistShape` (neither a canned gesture, so hand-rolled), `handSpan` for two-hand scale, `handTwist` for the single-hand rotate (`handAngle` kept for `hands.js`'s diagnostic readout, no longer used by the manipulator — see Phase 4).
- `overlay.js` — canvas skeleton, fingertip emphasis, and per-hand labels.

**Done looks like:** Hand skeleton + a live gesture label render over the webcam feed, holding a stable frame rate in the neighborhood of the SINUS paper's benchmark (25–30 FPS), tested at the paper's validated sweet spot of 0.5–1.0m from the camera. **Not yet confirmed — this machine has no webcam (0 video inputs), so the live half of this is untested.**

**Verified 2026-09-05 without a camera** (by feeding a blank canvas to the recognizer and synthetic landmarks to the maths/overlay):
- Model init 615ms; inference 14.4ms/frame ≈ 69fps ceiling, comfortably above the 25–30fps target.
- Timestamp guard holds against repeated and backwards timestamps.
- Pinch ratio 0.05 pinched / 1.16 open, and **provably scale-invariant** — identical ratios at 0.25×, 0.5×, 1×, 2× hand size.
- Aspect correction confirmed (equal horizontal and vertical gaps measure equal).
- Overlay draws correct skeleton topology, mirrors landmark x correctly, and keeps label text readable.
- Camera-denied/missing path shows a friendly message and re-enables retry.

**Sources to reference:**
- Google MediaPipe `GestureRecognizer` docs — canned gestures, `numHands` config, exact z-coordinate semantics (depth relative to wrist origin, same scale as x).
- Rahmawati, Andrean & Kustanto (2026), *Jurnal Ilmiah SINUS* 24(2) — FPS and confidence benchmarks, optimal distance.
- ASL project's `handTracker.js` (structure only — the classifier underneath is being replaced) and `overlay.js` (canvas drawing pattern, reused as-is).

**First live webcam test — 2026-09-05, on the Mac laptop via GitHub Pages:**
- **FPS: ~60 with one hand, dropping to ~40 or lower with two.** Above the 25–30 target either way. The two-hand cost is expected — it is a second inference pass per frame.
- **Handedness is correct**, and the two hands track independently with separate gestures. The suspected mirror inversion was wrong — that question is closed.
- **A real pinch reads ~0.15**, so the original `PINCH_THRESHOLD = 0.4` was far too loose. Tightened to **0.25**.
- **Bug found: a closed fist registered as a pinch**, especially with the back of the hand to the camera, and sometimes fired `Closed_Fist` and pinch simultaneously. Cause: pinch is measured in 2D projection, and in a fist the thumb and index tips collapse close together on screen. Measured on synthetic fist geometry, the gap ratio comes out at **0.178 — below even the tightened 0.25 threshold**, so tuning the threshold alone could not have fixed it. Fixed two ways: `Closed_Fist` from the recognizer now vetoes pinch outright, and a geometric guard (`MIN_PINCH_REACH`) rejects any pinch whose midpoint sits too close to the wrist, since a real pinch happens out at the fingertips while a fist curls everything back toward the palm. Synthetic separation is 1.67 (pinch) vs 0.70 (fist) against a 1.15 cutoff — **still needs confirming against a real hand**, which is why the live readout now prints `gap`, `reach` and per-fingertip distances.
- **Landmark accuracy degrades under fast motion, worst at the thumb.** Inherent to MediaPipe rather than something this code causes; the thumb is its least stable joint. Phase 4's stabilizer addresses the resulting action misfires, though not the landmark drift itself.
- **Resolved 2026-09-05:** pinch stays **thumb-to-index only**. Thumb-to-middle/ring/pinky deliberately do not register — those combinations are reserved as free slots for future gestures rather than folded into "pinch". Keeps the vocabulary unambiguous and means a later thumb+middle gesture can't collide with scale.

**Second live test — 2026-09-05, after the fix:**
- **The fist false positive is fixed and confirmed on a real hand.**
- One follow-on bug found and fixed: the label drawn under each hand still printed a bare gap number for a rejected pinch, so a blocked fist read as `pinch 0.18`. Pinch state is rendered in two places (the readout panel and the canvas label) and only one had been updated — they now share a single formatter.
- **`MIN_PINCH_REACH` calibrated from real hands: a deliberate pinch averages ~1.20.** The initial 1.15 left only 0.05 of margin, and since that figure is an average, the frames below it would have dropped the pinch mid-gesture. Loosened to **1.00**, verified by sweep: 0.70–0.87 rejects as curled, 1.00+ accepts. The guard can afford to be loose because `Closed_Fist` is the primary veto and this only backstops the back-of-hand case the classifier misses.
- **GitHub Pages caching was masking deploys.** Pages sends `Cache-Control: max-age=600` with no way to override it, so pushes stayed invisible on the test machine for ten minutes. Each entry point now stamps a version onto its module URL and propagates it to sibling imports; a `loaded HH:MM:SS` marker in the HUD makes a stale page obvious.

**Known risks / unknowns:**
- **`MIN_PINCH_REACH = 1.05`, and the margin is genuinely tight.** Measured on real hands: a pinch averages ~1.20, a fist with the back of the hand turned reads ~0.90 — only 0.30 apart, so the cutoff sits midway with 0.15 either side. Real fists ran higher than the synthetic 0.70 estimate, which is why this moved from 1.15 → 1.00 → 1.05 rather than settling first time. If fists start registering as pinches again, raise it; if pinches drop out mid-gesture, lower it. The `Closed_Fist` classifier veto remains the primary defence.
- Pinch is exposed as a raw per-frame threshold with **no hysteresis**, so it will chatter when held near the boundary. That is deliberate — Phase 4 inserts the ASL project's `stabilizer.js` between this and any action, and duplicating it here would pre-empt that.
- Detection/tracking confidence (80–95%) is validated under good lighting only — accuracy is known to drop at 1.5m+, in low light, and under occlusion. Treat this as a documented limitation, not a Phase 1 blocker.

## Phase 3 — Make It Look Like a Hologram ✅ Done (2026-09-05)

**What got built:** `threejs-vanilla-holographic-material`'s `HolographicMaterial` (MIT), vendored verbatim as `HolographicMaterial.js` rather than installed — the source repo is a private Vite demo, not an npm package, and the reusable part is one self-contained file (imports only from `three`). Applied to every mesh in the trimmed chair via `object.traverse()`, in both `main.js` and `hologram.js`; `.update()` is called once per frame from `scene.js`'s `onTick` hook to advance the animated time uniform.

**Done looks like:** The same Phase 2 model renders with a visible Fresnel rim-glow and animated scanline/signal effect instead of its default material, with at least fresnel amount, color, and brightness confirmed tunable live. **Confirmed 2026-09-05:** rim glow and scanlines both visibly present; the time uniform measurably advances frame to frame; color, fresnel amount, and brightness were each changed live via `window.hologram.material.uniforms` and re-rendered correctly (cyan/subtle → hot pink/high-brightness, confirmed by screenshot, not just by reading the uniform back). Gesture manipulation (Phase 4) still applies cleanly to the holographic mesh — scale/rotate/position are unaffected by the material swap, verified directly.

**Sources to reference:**

## Phase 4 — Gesture-Driven Manipulation

**What gets built:** Wire the Phase 1 gesture interpreter to the Phase 3 hologram. **Gesture mapping revised 2026-09-05 (11) from live testing** — the original plan below (two-hand angle-delta rotate) turned out to feel "janky and cluttered" in practice; see that revision entry for the full story. Current mapping: a closed fist both moves the object (wrist position) and rotates it (twisting the wrist like turning a doorknob, mapped to a lazy-Susan spin around the object's vertical axis); two-hand pinch scales it. Still to build: depth-based push/pull, and a two-hand pull-apart gesture driving **explode — promoted to v1 scope, dual-mode (2026-09-04):**
- *Literal explode* (multi-part meshes): each part translates outward from the object's centroid along its own centroid-to-part vector, scaled by hand-distance.
- *Stretch/expand* (single-mesh objects, e.g. the chair): the same pull-apart motion instead applies a scale/stretch transform to the whole hologram, since there's no separate geometry to pull apart.
- *Mode selection:* auto-detected at GLB load time from the model's mesh count (>1 distinct mesh node → literal explode available; 1 → stretch/expand only), plus a manual override toggle for edge cases (e.g. scan noise welding multi-part geometry into one mesh). An on-screen HUD indicator (same pattern as the Phase 1 gesture-label overlay) shows which mode is currently active and updates on load or toggle.

Port the ASL project's `stabilizer.js` hysteresis so gestures don't misfire on single noisy frames.

**Done looks like:** All v1 gestures (pinch-scale, fist-grab-move-and-rotate, push/pull, dual-mode explode) work live on the actual hologram from Phase 3, holding up under the same 25–30 FPS / 0.5–1.0m conditions validated in Phase 1, with no visible single-frame jitter thanks to the stabilizer. **Confirmed 2026-09-05 on a real webcam:** grab (move + rotate) and two-hand pinch-scale both work; the priority right now is making that core set reliable before building push/pull or explode, per explicit direction from live testing — see revision (11). Literal explode's "done" is partial until a multi-part object is scanned — see Known risks.

**Sources to reference:**
- `collidingScopes/3d-model-playground` and `threejs-handtracking-101` — closest interaction-model matches.
- `heeelol/jester` — validates the two-hand pinch-to-scale / angle-to-rotate mapping specifically.
- `DareDev256/hand-playground` — "3D Cube" and "Grab & Toss" exercises as close templates for grab/rotate/scale state machines.
- Microsoft MixedReality-UXTools `TwoHandManipulationRotateLogic` — reusable, platform-agnostic rotate math.
- ASL project's `stabilizer.js` — hysteresis logic ported directly.
- Codrops/Hackaday DIY hand controller — middle-finger + wrist landmarks for depth/positioning, closed-fist for grab, plus collision detection for interactivity.

**Known risks / unknowns:**
- `TonyViT/HybridHandInteractions` flags that hand tracking gets *less* reliable specifically while gripping something — a real failure mode to design around during grab/move, not just scale/rotate.
- MediaPipe's landmark depth (z) is relative and less reliable than x/y — adequate for a push/pull gesture, but not true 3D position. This is where the project's stated edge over prior art applies: because Phase 0's asset is a real LiDAR scan with true geometry, depth interaction can be designed against real mesh geometry rather than the landmark-distance proxy every reference project relies on — worth deciding explicitly in this phase rather than defaulting to the proxy purely out of habit.
- **Literal explode is unverified until a second, multi-part object exists.** The chair (Phase 0's chosen object) is a single continuous mesh, so it only exercises the stretch/expand branch. Literal explode's mesh-separation logic can be built and unit-tested against a synthetic multi-mesh GLB, but "done" for that branch specifically means scanning a second, genuinely multi-part object. **Open question, needs your input:** schedule that second scan now, or defer it.
